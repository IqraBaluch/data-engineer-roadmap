## 1. Three kinds of COUNT

| Expression | Counts | Result on `emp` |
|---|---|---|
| `COUNT(*)` | rows | 7 |
| `COUNT(salary)` | rows where salary is not NULL | 6 |
| `COUNT(department)` | rows where department is not NULL | 6 |
| `COUNT(DISTINCT department)` | different non-NULL values | 3 |

```sql
SELECT COUNT(*)                   AS total_rows,
       COUNT(salary)              AS with_salary,
       COUNT(department)          AS with_department,
       COUNT(DISTINCT department) AS distinct_departments
FROM emp;
```

- `COUNT(*)` counts **rows, not cells**: 7 employees, however many columns the table has.
- **Always alias aggregates.** Unnamed ones all come back as `count`, and the VS Code results grid showed wrong values (7, 3, 3, 3) until each column had its own name.

## 2. SUM, AVG, MIN, MAX skip NULLs

```sql
SELECT SUM(salary) AS total,     -- 39000
       AVG(salary) AS average,   -- 6500
       MIN(salary) AS lowest,    -- 4000
       MAX(salary) AS highest    -- 9000
FROM emp;
```

**The AVG trap:** AVG divides by the number of **non-NULL** values.

| Calculation | Result | Meaning |
|---|---|---|
| `AVG(salary)` | 39000 / 6 = 6500 | average of employees who have a salary |
| `SUM(salary) / COUNT(*)` | 39000 / 7 = 5571 | Nadia counted as zero |
| `AVG(COALESCE(salary, 0))` | 5571 | same as above, written explicitly |

In an interview, ask which one the business wants.

## 3. GROUP BY: one summary row per group

GROUP BY sorts the rows into piles, one per value, then aggregates inside each pile.

```sql
SELECT department,
       COUNT(*)    AS employees,
       SUM(salary) AS total_salary
FROM emp
GROUP BY department;
```

| department | employees | total_salary |
|---|---|---|
| IT | 2 | 16000 |
| Sales | 2 | 13000 |
| HR | 2 | 6000 |
| NULL | 1 | 4000 |

- **NULLs form their own group.** WHERE comparisons drop NULL rows; GROUP BY gathers them into one pile. So 4 rows, not 3.
- HR's total is 6000 (SUM skips Nadia's NULL), but its count is 2 (`COUNT(*)` counts rows).
- **The GROUP BY rule:** every column in SELECT must be in the GROUP BY or inside an aggregate.
- A group can be defined by several columns: `GROUP BY actor_id, director_id` makes one pile per combination.

## 4. HAVING vs WHERE

| | Filters | Runs | Can use aggregates? |
|---|---|---|---|
| WHERE | individual rows | before GROUP BY | No |
| HAVING | whole groups | after GROUP BY | Yes |

```sql
-- Fails: WHERE runs before the groups exist, so there is nothing to count
SELECT department, COUNT(*) AS employees
FROM emp
WHERE COUNT(*) > 1
GROUP BY department;

-- Correct: make the piles, then filter the piles
SELECT department, COUNT(*) AS employees
FROM emp
GROUP BY department
HAVING COUNT(*) > 1;
```

- **Written order follows the frog:** ... **G**ROUP BY, then **H**AVING. Writing HAVING first is a syntax error.
- An aggregate can be used in HAVING without appearing in SELECT.
- **Do I need HAVING?** Ask: "Is there a condition on the groups?" If the task wants every group, there is no HAVING.

## 5. Conditional aggregation

Count or sum **only the rows that meet a condition**, while still reading every row. Put a CASE inside the aggregate.

```sql
SELECT department,
       COUNT(*) AS employees,
       SUM(CASE WHEN salary >= 7000 THEN 1 ELSE 0 END) AS high_earners
FROM emp
GROUP BY department;
```

| department | employees | high_earners |
|---|---|---|
| IT | 2 | 2 |
| Sales | 2 | 1 |
| HR | 2 | 0 |
| NULL | 1 | 0 |

- WHERE can't do this: it would remove the other rows, and departments with no high earners would disappear.
- **Signal in the question:** "count X *and* count Y" or "percentage of X" in the same result → conditional aggregation.

**Does CASE need ELSE?**

| Pattern | ELSE? |
|---|---|
| `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` | Yes. Without it, a group with no matches returns NULL instead of 0 |
| `COUNT(CASE WHEN ... THEN 1 END)` | **No.** COUNT counts non-NULL values, so `ELSE 0` would count every row |

**Percentage of rows:**

```sql
SUM(CASE WHEN rating < 3 THEN 1 ELSE 0 END) * 100.0 / COUNT(*)
```

Part on top, whole (`COUNT(*)`) below, times 100.

## 6. Traps from the problems

**Integer division.** In PostgreSQL, whole ÷ whole drops the decimals: `5 / 2 = 2`, `1 * 100 / 3 = 33`. Add `.0` to one side: `rating * 1.0 / position`, `* 100.0`.

**ROUND needs numeric.** `ROUND(x, 2)` with decimals only works on the `numeric` type. If a column is `double precision` (as on DataLemur), cast it first:

```sql
ROUND((expression)::numeric, 1)      -- PostgreSQL shortcut
ROUND(CAST(expression AS numeric), 1) -- standard SQL
```

**Weighted average.** When one row stands for many things (a "compressed" table), multiply inside the SUM before adding:

```sql
SUM(item_count * order_occurrences) * 1.0 / SUM(order_occurrences)
```

`AVG(item_count)` would be wrong: it treats every row as one order.

**When is GROUP BY needed?** Only when the answer needs one row *per* something. No "per", no GROUP BY. Grouping by `device_type` when one total row was wanted produced a row per device, full of zeros.

**"Has all of X, Y and Z".** Filter to those values, group, then keep groups with exactly that many rows:

```sql
WHERE skill IN ('Python', 'Tableau', 'PostgreSQL')
GROUP BY candidate_id
HAVING COUNT(*) = 3
```

`= 3`, not `> 3`: after the WHERE, nobody can have more than three. `IN (...)` is shorthand for several `OR`s.

```sql

```

## 8. Interview questions I can now answer

**COUNT(\*) vs COUNT(col) vs COUNT(DISTINCT col)?**
`COUNT(*)` counts all rows. `COUNT(col)` skips rows where the column is NULL. `COUNT(DISTINCT col)` counts different non-NULL values.

**Difference between WHERE and HAVING?**
WHERE filters rows before grouping and can't use aggregates. HAVING filters groups after grouping and can.

**Is AVG(salary) the same as SUM(salary) / COUNT(\*)?**
Only when there are no NULLs. AVG ignores NULL values, so it divides by fewer rows.

**How does GROUP BY treat NULL?**
All NULLs go into one group of their own.

**How do you find duplicate values in a column?**
`GROUP BY` the column and keep groups `HAVING COUNT(*) > 1`.

**How do you compute several filtered metrics in one query?**
Conditional aggregation: `SUM(CASE WHEN condition THEN 1 ELSE 0 END)` for each metric, in one pass over the table.

**Ratio of sums vs average of ratios?**
They answer different questions. Weighted data needs `SUM(a * b) / SUM(b)`, not `AVG(a)`.

## 9. Mistakes I made

- Thought `COUNT(*)` counts every cell (7 rows × 3 columns = 21). It counts rows: 7.
- Wrote HAVING before GROUP BY, twice.
- Added `COUNT(*)` to SELECT when the task asked for one column only.
- Added a HAVING when the task had no condition on the groups.
- Wrote `>= 1` where the task said "at least three".
- Forgot that 7000 counts for `>= 7000` (the "at least" trap again).
- Wrote `position / rating` and `position % rating` instead of `rating / position`. `%` is remainder, not division.
- Integer division: `* 100` gave 33 instead of 33.33.
- Used `COUNT(rating < 3)`, which counts every row, true or false.
- Added a GROUP BY when the answer was a single total row.
- Used `> 3` instead of `= 3` for "has all three".
- Biggest lesson: **read the task twice** before writing anything, and work one example by hand.
