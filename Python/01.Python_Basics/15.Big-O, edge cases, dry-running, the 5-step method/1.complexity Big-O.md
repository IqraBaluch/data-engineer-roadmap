# Complexity (Big-O)

## Big-O in one line
How many more steps does the code need when the input gets bigger?
`n` = size of the input. Use the WORST case, and drop constants (2n is O(n)).

## The common ones, from fast to slow
| Big-O | Name | Example |
|---|---|---|
| O(1) | constant | `items[0]`, `d[key]`, `d.get(key)`, `x in my_set`, `set.add(x)` |
| O(log n) | logarithmic | (later) searching a sorted list by halving |
| O(n) | linear | one loop over n items |
| O(n log n) | | `sorted(nums)` |
| O(n squared) | quadratic | a loop inside a loop over the same n items |

## Rules
- One loop AFTER another: ADD (n + n = O(n)).
- A loop INSIDE a loop: MULTIPLY (n * m, or n * n = O(n squared)).
- Different sizes get different letters: n words, m letters gives O(n * m).
- When two parts are added, the bigger one wins (sorted + loop = O(n log n)).
- Quick test: look at the indentation. Second loop at the same level after the first ends = add. Second loop inside the first one's body = multiply.

## Lookups
- dict / set lookup: O(1) (jumps straight to it).
- list search (`x in my_list`, `.index`): O(n) (checks one by one).
- list by POSITION (`items[i]`): O(1).
- Same loop, different structure:
  - `seen = set()` gives time O(n), space O(n)
  - `seen = []` gives time O(n squared), space O(n)

## Space
- Count what the code CREATES: `x = sorted(...)`, `x = list(...)`, a new dict, a Counter, a result list = a new structure of size n.
- A Counter or dict has one key per DIFFERENT item. Lowercase letters: at most 26 keys, so O(1). Numbers (no ceiling): up to n keys, so O(n).
- Worst case: "no duplicate" means the set or list holds everything, so O(n).
- Only a few single variables (like `best` and `profit`): O(1).

## Trade-off
Dictionary Two Sum: time O(n) instead of O(n squared), but extra space O(n). Memory is swapped for speed.

## Brute force
The simplest way: try every possibility (every pair). Always works, usually slow.
Say it in an interview: "The brute force is O(n squared). Can I do better?"
